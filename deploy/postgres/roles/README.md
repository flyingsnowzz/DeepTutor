# Runtime PostgreSQL roles

Run Alembic with the table-owning migration connection first. Then run
`deploy/postgres/init/01_app_role.sql` and `02_auth_role.sql` in that order
against the target database as its owner/superuser. Both scripts grant
`CONNECT` on the database to which `psql` is connected, so a clean database
such as the local rehearsal's `deeptutor_prod` can live alongside a
test-populated development database. Always run `02_auth_role.sql` last: it
removes the data role's credential-table privileges.

```bash
psql -v ON_ERROR_STOP=1 -d deeptutor_prod -f deploy/postgres/init/01_app_role.sql
psql -v ON_ERROR_STOP=1 -d deeptutor_prod -f deploy/postgres/roles/02_auth_role.sql
psql -d deeptutor_prod
```

In the interactive `psql` session, set separate random passwords without
putting them in shell history:

```text
\password deeptutor_app
\password deeptutor_auth
ALTER ROLE deeptutor_auth LOGIN;
```

Use `deeptutor_app` in runtime `DATABASE_URL`, `deeptutor_auth` in
`AUTH_DATABASE_URL`, and the table owner only for Alembic and ETL. The
application rejects a restricted data connection without a separate auth
connection. `deeptutor_auth` can access the six account tables listed
in the SQL script and the MarginNote 4 device-token index; it bypasses RLS
so login or device sync can find an owner before knowing the user ID.
`deeptutor_app` cannot read either password table or the device-token index.

Check the grants after applying the script:

```sql
SELECT has_table_privilege('deeptutor_app','admin_accounts','SELECT'),
       has_table_privilege('deeptutor_app','first_party_credentials','SELECT'),
       has_table_privilege('deeptutor_auth','admin_accounts','SELECT'),
       has_table_privilege('deeptutor_auth','first_party_credentials','SELECT');
```

The expected result is `false, false, true, true`. Keep the migration
connection and database dumps outside the Web process. A PostgreSQL dump
does not restore role passwords; retain role setup and secrets separately
for rollback or disaster recovery.

## Claim an imported local account

The SQLite importer creates a stable `legacy_...` ordinary-user ID without
a Web password. After the final SQLite import and a validated PostgreSQL
backup, use the offline claim command to attach a first-party login to that
existing ID. The command preserves session, Mastery, assessment, and receipt
ownership; it does not copy or rewrite those rows.

```bash
# First call only checks eligibility and username availability.
DATABASE_URL="$MIGRATION_DATABASE_URL" python -m scripts.migration.sqlite_to_postgres.claim \
  --owner legacy_62ec318f44ec9004 --username imported_local

# Create a private password file using your deployment secret manager.
DATABASE_URL="$MIGRATION_DATABASE_URL" python -m scripts.migration.sqlite_to_postgres.claim \
  --owner legacy_62ec318f44ec9004 --username imported_local \
  --execute --password-file /private/path/initial-password
```

The password file must have mode 0600. This command requires the table-owner
migration role and an existing `migration_batches` receipt. It refuses an
already claimed owner, an inactive/non-user account, or a username collision.
Use the newly claimed ordinary account at `/api/auth/login`; administrators
still use their separate login and account store. For rollback, restore the
validated PostgreSQL dump together with the saved role setup and secrets.
Any second legacy source directory needs an explicit account decision and
must not be silently merged into this owner.

## Copy file-backed content

After importing the SQLite metadata, copy the ordinary user's workspace
files and immutable presentation snapshots into the claimed user's new home.
The importer records the old general-workspace ID as a per-owner presentation
alias so historical `/files/workspace-items/...` links remain readable.

```bash
python -m scripts.migration.sqlite_to_postgres.copy_content \
  --source-home data/user \
  --target-home data/users/legacy_62ec318f44ec9004/user \
  --manifest /private/path/content-manifest.json

python -m scripts.migration.sqlite_to_postgres.copy_content \
  --source-home data/user \
  --target-home data/users/legacy_62ec318f44ec9004/user \
  --execute --manifest /private/path/content-manifest.json
```

The command hashes every copied file, refuses differing destination files
and symlinks, and can be rerun. It excludes SQLite databases and runtime
settings, which remain in the frozen rollback source. Copy the content
manifest and the PostgreSQL dump to the server alongside the actual file
tree; the dump alone does not contain uploaded or generated bytes. Verify
historical attachment URLs through the authenticated Web API before opening
traffic.
